> **Prompt template for AI-assisted implementation:**
> "I am building the BCIS Subscription Billing and Collection System. This is Phase 1: Project Foundation.
> Set up a pnpm monorepo with three workspaces: `apps/client` (Electron + React + TypeScript),
> `apps/server` (Fastify + TypeScript + Drizzle ORM), and `packages/shared` (shared types and utilities).
> Configure ESLint, Prettier, TypeScript strict mode, and Drizzle Kit. Create the initial
> PostgreSQL connection, a health-check route on the server, and a minimal Electron shell that

## 1. Overview

Phase 1 establishes the **entire project skeleton**. No business logic is written here.
The goal is: one command starts the server, one command opens the Electron app, and the app
confirms it can reach the server. Every developer who joins later will understand the structure
immediately by reading the folder names and a single README.

```
┌─────────────────────────────────────────────────────────┐
│  Office LAN (3 desktop PCs)                             │
│                                                          │
│  PC-1 (Server + Client)      PC-2 (Client only)         │

│  │  ──── IPC ────       │    │  ──── HTTP ────    │     │
│  │  Fastify API Server  │    │  → API on PC-1     │     │
│  │  ──── SQL ────       │    └────────────────────┘     │
│  │  PostgreSQL DB       │                                │
│  └──────────────────────┘    PC-3 (Client only)         │
│                              ┌────────────────────┐     │
│                              │  Electron App      │     │
│                              │  React UI          │     │
│                              │  ──── HTTP ────    │     │
│                              │  → API on PC-1     │     │
│                              └────────────────────┘     │
└─────────────────────────────────────────────────────────┘
```

**Key constraint from lab material:**
> "Renderer direct database access" is a **critical failure condition**.
> The React renderer NEVER touches the database. All data flows through the Fastify API.
> Electron main process is only used for OS-level features (file dialogs, print, system tray).

## 4. Technology Decisions

| Layer | Technology | Reason |
|-------|-----------|--------|
| Desktop shell | Electron v32+ | Required by lab spec; OS print dialogs, file system |
| UI framework | React 18 + TypeScript | Mature, large community, works in Electron |
| UI components | shadcn/ui | Copy-paste components — readable, no hidden magic |
| Styling | Tailwind CSS | Consistent spacing and color system |
| State management | Zustand | Minimal boilerplate — open a store file and understand it |
| HTTP client | Axios | Readable interceptors for auth tokens and error handling |
| API server | Fastify v5 | Fast, TypeScript-native, schema validation built in |
| ORM | Drizzle ORM | SQL-like queries, type-safe, migrations via Drizzle Kit |
| Database | PostgreSQL 16 | Required — supports 3 concurrent clients reliably |
| Validation | Zod | Schema shared between client and server |
| Build tool | Vite + electron-vite | Fast HMR, Electron-aware bundling |
| Package manager | pnpm | Workspace support, fast, disk-efficient |
| Linting | ESLint + Prettier | Enforced, consistent code style |
| TypeScript | Strict mode | Catches bugs at compile time, not runtime |

### Why NOT these choices:
- **SQLite** — violates lab requirement; cannot support 3 concurrent PC connections
- **tRPC** — adds abstraction that makes HTTP calls non-obvious during defense questioning
- **Redux** — too much boilerplate for a 3-role system; Zustand does the same in less code
- **NestJS** — decorator-heavy, hides what the server actually does; Fastify is transparent

## 5. Environment Configuration

All configuration lives in one file. No magic strings scattered through the codebase.

```typescript
// apps/server/src/config.ts
// Everything the server needs to know about its environment.
// Change a variable here → it propagates everywhere automatically.

import { z } from "zod";

const envSchema = z.object({
  NODE_ENV: z.enum(["development", "production", "test"]).default("development"),
  PORT: z.coerce.number().default(3003),
  DATABASE_URL: z.string().url(),
  JWT_SECRET: z.string().min(32, "JWT secret must be at least 32 characters"),
  CORS_ORIGIN: z.string().default("http://localhost:5173"),
  BCRYPT_ROUNDS: z.coerce.number().default(12),
});

export const config = envSchema.parse(process.env);
// If any required variable is missing → server crashes immediately with a clear error message.
// This is intentional. Silent misconfiguration is worse than a loud crash.
```

`.env.example` (committed, no real secrets):
```env
NODE_ENV=development
PORT=3003
DATABASE_URL=postgresql://bcis_user:change_this@localhost:5432/bcis_db
JWT_SECRET=change_this_to_a_long_random_string_at_least_32_chars
CORS_ORIGIN=http://localhost:5173
BCRYPT_ROUNDS=12
```

## 6. Drizzle ORM Configuration

```typescript
// drizzle.config.ts (root of monorepo)
import { defineConfig } from "drizzle-kit";

export default defineConfig({
  schema: "./apps/server/src/db/schema/index.ts",
  out: "./apps/server/src/db/migrations",
  dialect: "postgresql",
  dbCredentials: { url: process.env.DATABASE_URL! },
  verbose: true,  // shows SQL being generated — useful during dev
  strict: true,   // requires manual confirmation before destructive migrations
});
```

```typescript
// apps/server/src/db/connection.ts
// The one place in the codebase that holds the database connection.
// Import `db` from here whenever you need to run a query.

import { drizzle } from "drizzle-orm/node-postgres";
import { Pool } from "pg";
import { config } from "../config";
import * as schema from "./schema";

const pool = new Pool({
  connectionString: config.DATABASE_URL,
  max: 10,                   // supports 3 concurrent clients with room to spare
  idleTimeoutMillis: 30_000,
  connectionTimeoutMillis: 2_000,
});

export const db = drizzle(pool, {
  schema,
  logger: config.NODE_ENV === "development",  // logs SQL in dev, silent in prod
});
```

## 10. CLAUDE.md — AI Assistant Instructions

```markdown
# BCIS System — AI Development Instructions

## Project context
Subscription Billing and Collection System for a cable/internet ISP.
3-PC office environment. Electron + React frontend, Fastify API, PostgreSQL.

## Non-negotiable rules
1. NEVER put database queries in the React renderer or Electron main process.
   All data access goes through the Fastify API only.
2. NEVER delete financial records destructively. Use soft-delete or reversal patterns.
3. NEVER store passwords in plaintext. Always bcrypt with >= 12 rounds.
4. NEVER hardcode secrets. All config comes from environment variables via config.ts.
5. ALL monetary amounts stored as integers (centavos). Never use JavaScript floats for money.
   Example: PHP 150.50 = 15050 centavos in the database.

## Code readability principles
- Name things for what they DO: calculateMonthlyInvoice() not calcInv()
- One responsibility per function. Two responsibilities = split into two functions.
- If a business rule needs explaining, add a comment — don't be clever
- Prefer explicit over implicit: status === "active" not !!status
- Avoid abbreviations in variable names unless they are universally understood (e.g., id, url)

## File organization
- One domain feature per folder under modules/
- Schema files match domain: billing.ts contains billing tables only
- Never mix two domain's logic in the same file

## When implementing a feature, do it in this order:
1. Read the spec for that phase
2. Check existing schema in db/schema/ and types in packages/shared
3. Write or update the Drizzle schema
4. Run db:generate and review the migration SQL
5. Write the Zod validation schema
6. Write the Fastify route handler
7. Write the React page/component
8. Write at least one test for any financial calculation
9. Run typecheck + lint + test before committing
```
